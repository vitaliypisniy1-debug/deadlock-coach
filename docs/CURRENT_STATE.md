## 0.15.1 — «После выигранной драки — объект»

Второе улучшение из разведки: «Мои матчи» → «Решения по карте» получает строку «После выигранной драки — объект». После 20:00 ищутся решающие драки (≥3 погибших соперников, перевес ≥2 — размен 3:2 уже не считается окном), и проверяется окно 60 секунд на Midboss/объект по данным `objectives` и `midBoss`. ## 0.16.0 — «Справочник контрпиков и контрпредметов»

Новый раздел «Справочник контрпиков» (меню «Мета») с входами из «Меты героев» (страница героя → «Кого взять против него») и «Перед игрой» («Справочник по сопернику»). Игрок выбирает героя соперника и получает: (а) «Кого взять» — таблица героев с результатом против него минус их обычный винрейт в той же выборке (отдельно линия и души к 9-й минуте), (б) «Что купить» — покупки топов против него (lift против игр без этого героя) и ответы из проверенных механик.

Основание выводов видно у каждой рекомендации: статистика матчапов (Deadlock API, `/v1/analytics/hero-counter-stats` + `hero-stats`, 14 дней, ранг Фантом 1+ с фолбэком), покупки топов (`counterTable`/`counterItems`, lift ≥ 1.5) или механика из файлов игры (deadlock.gs, build 6861, патч Halloween 2026-10-30; правила в `src/core/counterRules.js` — после патча обновляется одно правило). Расчёты не дублируются: контрпики считаются `pairDelta`/`baseWr`/`laneSouls` из `pick.js` поверх того же `pickmeta.json`, что и совет по пику.

Честность: контрпик — только фактическая положительная разница (пары < 100 игр скрыты, 100–300 помечены «мало игр», малые выборки стянуты к нулю при ранжировании); «сильный герой» не выглядит контрпиком против всех — сравнение с его базой; при отсутствии плюсовых пар раздел говорит «разница в пределах шума», а не подставляет советы; популярный предмет не выдаётся за контрпредмет (в таблицу покупок попадает только lift ≥ 1.5); механические ответы помечены «проверь в игре», где применимость выведена из типов эффектов. Механики героев разобраны для Apollo (77), Victor (66), Lash (31) и Infernus (1) — чем опасен, чем лечится, что против него; для остальных 40 героев — только статистика и покупки, без выдуманных объяснений. Ответ кэшируется по герою (`codex:lookup` + `S.codex.data`): смена соперника — 100–115 мс, без новых запросов к сети; при сбое сети показываются сохранённые данные с датой и текстом ошибки.

Проверено 12.11.2026:

- `npm test` — 66 тестов (64 прежних + 2 новых: справочник на полном списке героев — метка `enemy` против смешения при смене героя, малая выборка, устаревшие данные, «популярный предмет — не контрпредмет», правила четырёх сквозных героёв; и `codexLookup` — ноль запросов к сети при смене героя, сохранённые данные при сбое обновления).

## 0.16.1 — «живучесть после серии смертей»

Новое правило в `gameLeaks` (ключ `survivability_purchase`, раздел «Предметы») и цель тренера. Условие: после 10:00 серия из 3+ смертей (между соседними ≤ 240 с), и с начала серии не куплено ни одного предмета живучести от 1 250 душ (`assets.items[id].slot === 'vitality'`). Правило не срабатывает, если живучесть покупалась после начала серии, если к началу серии уже было 2+ таких предмета («купи ещё» из данных не следует), если после последней смерти оставалось < 90 с игры (не было окна на покупку) или если каталог предметов не загружен (проверка невозможна — игра помечается непроверяемой, а не «чистой»). В тексте: тайминг серии, кто убивал, потери душ и какие покупки ≥ 1 250 душ шли не в живучесть. `context` прямо различает факт (серия и покупки) и гипотезу (помогла бы живучесть — проверяется в повторе).

Проверено 12.11.2026:

- `npm test` — 67 тестов (66 прежних + 1 новый: срабатывание с моментами и убийцами, покупка живучести после серии, живучесть уже собрана, смерти не подряд, нет окна на покупку, отсутствие каталога, попадание в профиль и цель тренера; NaN/undefined нет).
- Реальные матчи (копия профиля, только чтение): по 439 личным матчам правило сработало 3 раза — серии из 3–4 смертей без покупок живучести, с именами убийц, потерями душ и списком «не в живучесть» (Headhunter, Mystic Vulnerability и т. п.). В 16 матчах живучесть после серии покупалась — утечки нет; в 3 — уже была собрана; в 5 — не было окна; в 13 — смерти не серией.
- Производственный конвейер `sync.leaks()` на проверенной копии профиля: 9 266 матчей в хранилище, 30 игр в разборе, все прежние ключи утечек целы, битых строк 0, цель тренера формируется.
- UI на копии профиля (CDP): раздел «Ошибки» рендерит профиль, цель и все группы утечек, консоль чистая.
- Формат данных не менялся (`EXTRACT_V` 2), перекачка истории не нужна.
- Релиз опубликован: PR #10, merge `f0470ff`, [v0.16.1](https://github.com/vitaliypisniy1-debug/deadlock-coach/releases/tag/v0.16.1) — Actions зелёный, тег Latest, установщик и portable на месте (проверено 12.11.2026 через API). Изменённые файлы: `src/core/leaks.js` (правило `survivability_purchase` + константы `STREAK_GAP`/`VITALITY_COST`/`REACT_SECS` + цель в `leakProfile`), `package.json` (0.16.1), `release-notes/v0.16.1.md`, `test/run.js`, доки.

## Тренер: переработка (ветка `coach/rework`, не опубликовано, 13.11.2026)

Логика (`src/core/coach.js`, `src/main/sync.js`): одна главная цель и до двух запасных (`GOALS_MAX` 3); недельный срок плана убран; перед постановкой цель проверяется по последним 20 играм (`calibrate`: ≥70% выполнения — не берём; ≤15% — ступени), ступень закрывается так же, как цель (4 из 5 последних игр), счёт начинается заново; поле `why` (эпизод, «в N из M игр», победы с замечанием и без — только при ≥10 проверенных играх и ≥5 в каждой группе, сравнение с топами, связь с победой WIN_LINKS); `act`, `how`, `close`, `stuck`, `bestStreak`, `beforeText`/`nowText`, `finished`; замена цели `replaceKey`; цель `survivability_purchase` из эпизода «Ошибок» (1 — замечания нет, 0 — есть, null — игру проверить нельзя; считаются игры с 3+ смертями после 10:00). Проверено: `npm test` — 71 тест; копия реального профиля (только чтение оригинала): старый план из 5 целей читается, пересборка даёт честные планки, цель по живучести создаётся из реальной серии смертей (матч в хранилище) и ложный эпизод отклоняется. Не проверено: сборка `npm run dist`, новый вид экрана после работы дизайна, вход Steam.

Исследование «Уровень игры» (выполнено на 350 сохранённых матчах с известным рангом, 3 личных аккаунта с историей 88–261 игр): регрессия по 14 показателям с проверкой «на чужом аккаунте» даёт ошибку около 1 ранга на двух аккаунтах (корреляция скользящих окон по 15 игр 0,56–0,65) и обратный результат на третьем (−0,79); отображение значений через таблицу `RANK_BENCH` смещено на ~4 ранга вниз, потому что медианы сохранённых матчей по тем же показателям (`neu9`, `brk9`, `pu10`) значительно ниже таблицы (например, `pu10`: 0 против 4, `brk9`: 155 против 546 на 7-м ранге). Вывод: единый «ранг игры» показывать нельзя; нужен относительный подход (сравнение с топами на том же герое тем же конвейером и динамика собственных показателей). Причина расхождения `RANK_BENCH` с сохранёнными матчами (проверила сессия «Ошибки»): это эпоха матчей, а не определения признаков — все сохранённые матчи с известным рангом старше 30.09.2026 (до карты City), таблица — ноябрь 2026; текущая выборка API даёт медианы в диапазоне таблицы. Поэтому выводы исследования относятся к старой карте: на текущем патче единый ранг по показателям не проверен (нужны свежие матчи с известным рангом); таблицу по текущему патчу не отвергаем.

Решение владельца (13.11.2026): вместо «Уровня игры» — динамика и сравнение с топами на твоих героях (`src/core/progress.js`: окна по 15 игр, заметное изменение только при 8+ играх в каждом окне, критерий Манна — Уитни, z ≥ 1,64; топы — тем же конвейером, что цели тренера; замечания «Ошибок» на игру — в динамике) и достижения (`src/core/achievements.js`: цели тренера, серии «без смертей в одиночку» и «≤1 смерти до 10:00», паузы после поражения, рост показателей, личные рекорды на герое; игры без данных пропускаются и не прерывают серию; открытые ступени и «просмотрено» хранятся в `achievements-<id>.json`, победы и заходы в приложение ничего не открывают). Данные для экрана: `dc.progress({ markSeen })` → `{ progress, achievements, records, anyNew, games }` (только сохранённые матчи, без скачивания). Внешний вид — сессия редизайна.

## Незавершённые изменения и ограничения

- Пилот «Разобрать реплей» опубликован в `main` на GitHub (коммит `c8f32db`, 12.11.2026). Рабочая папка совпадает с этой веткой: все 63 файла `src/`, `test/`, `tools/` и `build/` сверены по SHA-256 с исходной папкой пилота, версия `package.json` осталась 0.14.5, `fzstd` — чистый JavaScript без нативного кода, поэтому `app.asar.unpacked` в сборке нет и это нормально. Папка `../deadlock-coach-city` без Git-истории осталась как копия, базой выпуска не является. `package-lock.json` в Git не входит, как и раньше.
- В предыдущей сессии в пилоте прошёл 61 тест и сверились 31 событие смерти одного публичного реплея. Второй реплей API не нашёл.
- Свежесть истории зависит от покрытия Deadlock API. Недостающие события, расхождение часов и неполные данные могут мешать привязке к эпизоду. Интерпретация Rift и ящиков требует проверки на реплеях.
- Playwright, Vitest, ECharts, DuckDB и Sentry отсутствуют в манифесте релиза. Диагностика опирается на локальные журналы, существующие тесты и ручные проверки.
