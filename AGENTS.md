# Deadlock Coach

## Перед работой

- Работай из корня Git-клона. Прочитай [контекст проекта](docs/PROJECT_CONTEXT.md), [текущее состояние](docs/CURRENT_STATE.md) и последние относящиеся к задаче записи [журнала](docs/CHANGELOG_AI.md).
- Выполни `git status --short --branch`, `git branch -vv` и `git log -5 --oneline`. Если нужна актуальность GitHub, выполни `git fetch origin` и сравни ветку с её upstream и `origin/main`. Уточняй, какой коммит и ветка являются базой задачи. Если работаешь без Git или сети, сообщи, что именно удалось проверить.
- Работай в ветке задачи. Если файлы уже изменены, сначала изучи `git diff` и `git diff --cached`. Сохрани чужие правки. Для независимой задачи используй отдельную ветку и рабочую папку, если они нужны. Перед коммитом проверяй список подготовленных файлов.
- Отвечай владельцу по-русски. Техническую работу выполняй самостоятельно. Крупные изменения стека, архитектуры и формата хранилища согласуй отдельно и обосновывай проверками.

## Данные, доступ и публикация

- Сохраняй историю матчей, совместимость данных и существующие сценарии. Не чисти профиль для диагностики. Тесты, которые меняют данные, запускай на изолированном профиле или проверенной копии. Учитывай, что код может выбрать старую папку профиля из `appData` даже при запуске с другим `userData`.
- Не меняй секреты, токены, параметры авторизации или учётные записи без отдельного разрешения. Не помещай в Git, Claude Projects, сторонний API или отчёты ключи, содержимое профиля, закрытые журналы, пути с персональными данными и файлы сессий.
- Push, слияние, теги и публикацию выполняй только в пределах разрешения владельца. Не применяй force push, `git reset --hard` и удаление веток для передачи работы. Повышение версии и попадание изменений в `main` могут запустить релизную сборку.

## Качество и передача

- Подтверждай игровые правила по патчу, режиму и версии данных. Различай механику, статистическую связь и гипотезу. Привязывай совет к эпизоду и указывай, каких данных не хватает. Балл пика сам по себе не равен шансу победы. Используй реальные данные для оценки аналитики. Синтетические примеры допустимы в автоматических тестах для проверки отдельных условий.
- Сохраняй девять разделов и оверлей. При визуальных изменениях проверяй читаемость кириллицы, размеры окон и происхождение используемых артов.
- После правок запусти `npm test` и проверки, соответствующие затронутому сценарию. Отдельно укажи результаты тестов, сборки, ручной проверки интерфейса и проверки на реальных данных. Наличие кода подтверждает реализацию, но не заменяет проверку.
- После значимых изменений обнови [CURRENT_STATE.md](docs/CURRENT_STATE.md) и добавь запись в [CHANGELOG_AI.md](docs/CHANGELOG_AI.md). Для передачи укажи задачу, ветку, коммит, незавершённые изменения, проверки и следующий конкретный шаг.
